# TDD 开发指南

## TDD 验证清单

在标记工作完成前，必须确认：

- [ ] 每个新函数/方法都有测试
- [ ] 每个测试都先看过它失败
- [ ] 每个测试都因正确原因失败（功能缺失，非语法错误）
- [ ] 只写了让测试通过的最小代码
- [ ] 所有测试通过
- [ ] 输出干净（无错误、警告）
- [ ] 测试使用真实代码（非必要的 mock 除外）
- [ ] 边界情况和错误已覆盖

**无法勾选所有项？说明跳过了 TDD，需要重新开始。**

## TDD 循环详解

### 🔴 RED: 编写失败的测试

**目标**: 写一个最小测试描述期望行为

**检查点**:
- 测试名是否清晰描述了期望行为？
- 测试是否测试了真实行为（而非实现细节）？
- 运行测试是否失败？

**问题自检**:
- 如果测试通过了，是测试写错了吗？
- 失败原因是功能缺失，还是语法错误？

### ⚡ 验证 RED

**目标**: 确认测试因正确原因失败

**命令示例**:
```bash
npm test -- --filter="新测试名"
```

**检查点**:
- 确认测试失败 (非错误)
- 确认失败原因是"功能缺失"
- 如果通过 → 测试有问题，修复测试

### 🟢 GREEN: 写最小代码通过测试

**目标**: 只写让测试通过的最少代码

**原则**:
- 不添加额外功能
- 不添加"可能有用"的代码
- 不预先优化

**问题自检**:
- 这是最小代码吗？
- 我是否添加了测试没有要求的功能？

### ⚡ 验证 GREEN

**目标**: 确认测试通过

**命令示例**:
```bash
npm test
```

**检查点**:
- 确认新测试通过
- 确认其他测试仍通过
- 确认没有警告

### 🔵 REFACTOR: 重构优化

**目标**: 改善代码质量而不改变行为

**原则**:
- 消除重复
- 改善命名
- 保持测试通过
- 不添加新行为

**问题自检**:
- 重构后测试是否仍然通过？
- 是否添加了新行为？

## 常见 TDD 错误

| 错误 | 修正 |
|-----|------|
| 测试先通过再写实现 | 必须先看到测试失败 |
| 测试因语法错误失败 | 修复语法，确保因功能缺失失败 |
| 一次写多个测试 | 一次只写一个测试 |
| GREEN 阶段写额外功能 | 只写让测试通过的最小代码 |
| 跳过 REFACTOR 也能通过 | REFACTOR 是可选的，但推荐 |
