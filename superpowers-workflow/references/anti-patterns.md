# 反模式: 常见错误与纠正

## 流程类错误

| 错误想法 | 正确做法 |
|---------|---------|
| "需求很简单，直接写代码" | 简单需求也需要设计，至少 5 分钟头脑风暴 |
| "先写代码，之后再补设计文档" | 设计批准前禁止任何实现行动 |
| "跳过计划，直接开发更快" | 没有计划的开发会返工多次 |
| "我自己做了设计，效果跟 brainstorming 一样" | 不一样。跳过 brainstorming = 跳过文档产出 + 跳过 writing-plans = 跳过 TDD 计划 = 跳过整个质量链 |
| "产出物验证门太形式化了" | 没有产出物 = 没有完成。设计文档 + 实施计划 + tasks.json 缺一不可 |
| "执行技能链断裂没关系，我自己写代码" | 执行技能包含 TDD + 两阶段审查，跳过 = 跳过全部质量保障 |

---

## TDD 类错误

| 错误想法 | 正确做法 |
|---------|---------|
| "太简单不需要测试" | 简单代码也会出错，测试只需 30 秒 |
| "我之后再补测试" | 后补的测试立即通过，证明不了任何事 |
| "已经手动测试过了" | 手动测试 = 临时验证，无法重复，无法回归 |
| "先写实现，测试只是形式" | 没有失败的测试，证明不了实现正确 |
| "执行技能已经处理 TDD 了，不用检查" | 必须验证执行技能是否真的被调用了。如果技能链断裂，TDD 就不存在。阶段 4 需要显式检查测试文件是否存在 |
| "这个任务没有测试文件也行，下一个" | STOP。TDD 合规检查：无测试文件 = 不允许进入下一个任务 |
| "写了代码但没有测试，先继续" | 删掉代码，从测试开始。保留未验证的代码 = 后补测试 |

---

## 验证类错误

| 错误想法 | 正确做法 |
|---------|---------|
| "应该没问题了" | 运行验证命令，看输出，然后声称 |
| "本地测过了，不用再验证" | 必须提供可重复的验证证据 |
| "测试通过就行，不用截图" | Web 应用必须用浏览器工具验证（参见 SKILL.md "Web 验证工具选择"）；非 Web 应用需提供命令行输出证据 |
| "编译通过 = 验证通过" | 编译通过 ≠ 功能正确。阶段 5 需要: 测试 + lint + (Web) Playwright e2e 验证 |
| "e2e 用例失败了，先提交再说" | STOP。失败 = 调用 systematic-debugging 修复，修完重跑，通过后才能声称完成 |

---

## 代码类错误

| 错误想法 | 正确做法 |
|---------|---------|
| "先保留作为参考" | 保留 = 会参考 = 后补测试，必须删除 |
| "删除 X 小时的代码太浪费" | 沉没成本谬误，保留未验证的代码才是技术债务 |
| "顺便重构一下相关代码" | 一个需求一个 PR，禁止夹带 |

---

## 调试类错误

| 错误想法 | 正确做法 |
|---------|---------|
| "bug 太奇怪，直接改代码试试" | 停止！调用 Skill(skill="superpowers:systematic-debugging") 系统化调试 |
| "我大概知道原因，直接修" | 必须验证假设，确认根因后修复 |
| "加个 try-catch 就好了" | 隐藏问题不是解决问题，找到根因 |

---

## 审查类错误

| 错误想法 | 正确做法 |
|---------|---------|
| "审查意见都得改" | 验证建议可行性，不盲目接受 |
| "审查者说什么就做什么" | 技术严谨性优先，有疑问时澄清 |

---

## 快速自检

如果发现自己有以下想法，立即停止:

- [ ] "先写代码再说"
- [ ] "测试之后再补"
- [ ] "应该没问题了"
- [ ] "保留这段代码以防万一"
- [ ] "直接改改看"
- [ ] "太麻烦了，跳过这一步"
- [ ] "我自己做了设计，不用调 brainstorming"
- [ ] "执行技能没调也没事，自己写一样"
- [ ] "编译通过了就行"
- [ ] "e2e 失败了先不管"

**出现以上想法时，回到对应阶段重新执行。**
